

## 转账业务设计思路文档


# 转账业务设计思路：从校验到并发安全

> 以“用户转账”为典型场景，梳理业务边界、设计考量、核心功能点及可复用架构。  
> 适合作为设计参考、代码审查清单或教学案例。

---

## 一、业务背景与目标

实现一个**安全、可扩展、高内聚**的转账功能，支持：
- 付款人向收款人转账指定金额
- 严格的前置校验，防止非法操作
- 并发场景下不出现重复扣款或余额超扣
- 错误信息清晰统一，前端可直接展示

---

## 二、业务边界与需要考虑的方面

### 1. 前置校验——我们要校验什么？
所有检查必须在核心扣款前完成，采用 **“存在性 + 合法性”** 二分法。

#### （1）存在性校验（实体是否有效）
| 检查对象 | 具体内容 | 失败时返回 |
|----------|----------|------------|
| 付款账户 | 付款人 ID 对应的账户是否存在、未被注销 | `ACCOUNT_NOT_FOUND` |
| 收款账户 | 收款人 ID 对应的账户是否存在、未被注销 | `PAYEE_NOT_FOUND` |
| 关联支付工具 | 如果涉及银行卡/钱包，需检查其状态 | `PAYMENT_METHOD_INVALID` |
| 币种账户 | 多币种场景需检查对应币种账户是否有效 | `CURRENCY_ACCOUNT_INVALID` |

#### （2）合法性校验（业务规则是否满足）
| 规则 | 检查内容 | 失败时返回 |
|------|----------|------------|
| 金额有效性 | 金额 > 0，小数位数符合币种要求（如 0.837 非法） | `AMOUNT_INVALID` |
| 余额充足 | 付款账户可用余额 ≥ 转账金额 + 手续费 | `INSUFFICIENT_BALANCE` |
| 账户状态 | 付款账户未被冻结，收款账户未被冻结 | `ACCOUNT_FROZEN` |
| 单日限额 | 付款人当日累计转账金额未超过限额 | `DAILY_LIMIT_EXCEEDED` |
| 操作权限 | VIP 专属大额转账、免手续费等规则 | `NO_PERMISSION` |

### 2. 核心业务——扣款与入账
- **原子扣款**：使用数据库原子更新语句，防止并发超扣  
  `UPDATE account SET balance = balance - #{amount} WHERE id = #{id} AND balance >= #{amount}`
- **入账**：收款方余额增加
- **事务控制**：扣款和入账必须在同一数据库事务中，保证一致性

### 3. 并发安全——多次点击问题
- **前端**：按钮点击后立即置灰
- **接口幂等**：引入唯一请求令牌（Token），存入 Redis，后端校验并一次性消费
- **数据库兜底**：原子 SQL + 必要时结合乐观锁（version）或悲观锁（SELECT ... FOR UPDATE）

### 4. 错误处理与返回
- **错误码常量化**：统一管理，方便前端多语言
- **业务异常**：`BusinessException(code)` 抛出，全局异常处理器捕获
- **返回格式**：`{ "code": "ACCOUNT_NOT_FOUND", "message": "付款账户不存在" }`

## 三、设计思路流程

```
用户请求 → Controller接收参数
       ↓
  Service.transfer()
       ↓
  ① 前置校验链（TransferValidator）
     ├── AccountExistValidator (@Order 1)
     ├── PayeeExistValidator  (@Order 2)
     ├── AmountValidator      (@Order 3)
     ├── BalanceValidator     (@Order 4)
     ├── FrozenValidator      (@Order 5)
     └── DailyLimitValidator  (@Order 6)
     （任何一步失败 → 抛出 BusinessException → 全局异常处理器返回错误 JSON）
       ↓
  ② 核心业务（事务内）
     - 执行原子扣款 SQL
     - 执行收款入账 SQL
     - 记录交易流水
       ↓
  返回成功
```

## 四、核心功能模块设计讲解

### 功能1：可扩展校验链
**设计原则**：开闭原则（对扩展开放，对修改关闭）  
**实现方式**：
- 定义 `Validator` 接口，方法 `void validate(Object request)`
- 每个校验规则一个类，实现该接口，并标注 `@Component` 和 `@Order`
- 校验链管理器使用 `@Autowired List<Validator>` 自动收集所有实现，并按 `@Order` 排序
- 新增规则只需新建类，无需修改任何已有代码

### 功能2：数据库原子操作防并发
**问题**：先查余额再扣款，并发下可能读到旧数据  
**方案**：将“检查余额”与“扣款”合并为一条 SQL  
`UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?`  
- 数据库行锁保证同一行数据串行更新
- 影响行数为 0 时表示余额不足，直接回滚事务

### 功能3：全局异常处理
**职责分离**：
- 校验器只负责发现违规时 `throw new BusinessException("ERROR_CODE")`
- `@RestControllerAdvice` 拦截异常，根据错误码组装统一返回格式
- 业务代码完全不用管返回结构

### 功能4：幂等性保障（防重复提交）
- 客户端进入转账页时，后端生成唯一 Token 返回前端
- 提交时携带 Token，后端检查 Redis 中是否存在
- 存在则放行并删除 Token，重复提交直接返回“请勿重复操作”

## 五、可复用总结

这套设计可直接迁移到任何需要“前置校验→核心操作”的业务，如：
- 下单：校验库存、优惠券、用户黑名单
- 提现：校验银行卡、最低提现金额、手续费
- 注册：校验用户名唯一、密码强度、验证码

只需替换具体校验规则，架构和设计模式完全不变。
