# 一、Redis能干什么？底层数据结构说了算

String：并不只是字符串，内部编码可能是int或者embstr/raw。这就让它天然能做计数器。
比如你写一个视频网站的播放量统计，直接INCR video:1001:views，原子自增，比数据库update count\=count+1快得多。用它还能存序列化后的对象，不过更推荐存小对象

Hash：底子可以是压缩列表或哈希表。最适合存对象属性。
比如用户购物车：HSET cart:user123 sku:001 2，商品id当field，数量当value，比String存一整个序列化对象灵活，因为你只需要改数量的时候不用整存整取

List：底层是一个快速列表，两头操作快。用它做简单的消息队列特别顺手。
比如订单完成后要发短信、推通知，你LPUSH order:msg:queue "msg\_data"，另一头BRPOP阻塞取，解耦且不会丢失消息

Set：无序不重复，跟Java的HashSet一样。做点赞、踩、共同好友很好用。
比如你给用户A和用户B的粉丝列表分别用Set存，SINTER followers:A followers:B 一下就得到共同粉丝了

Zset：这是“跳表”的用武之地。每个元素带个score，自动排序。
实时排行榜：ZADD hot:topics 1000 "苹果发布会"，然后ZREVRANGE hot:topics 0 9 withscores拿前十

# 二、跳表

为啥不用红黑树？因为跳表实现简单，而且做范围查找无敌。比如查分数在80到90分的人，跳表从顶层定位到80，然后顺着底层链表往后撸到90，一气呵成。你可以在纸上画一下：最底层是完整有序链表，上面每两个、四个节点抽一个当索引，查询时先走高速，再下沉，时间复杂度O(logN)，空间换时间

**案例**：你写一个校园论坛，用Hash存帖子内容，用String做浏览量，用Set存点赞用户id，用Zset按热度排行帖子，再用List当操作日志队列。一套下来，你就能体验到“数据结构驱动开发”是什么感觉。

# 三、Redis 为什么这么快

核心 4 大原因：

1. 纯内存存储：所有数据都在内存中，读写操作纳秒级完成，远快于磁盘 IO 数据库，绝大多数操作时间复杂度为 O (1)
2. 单线程模型：避免了多线程的上下文切换、锁竞争的 CPU 开销，无锁竞争，执行效率极高
3. 非阻塞 IO 多路复用（epoll）：基于 Linux epoll 实现 IO 多路复用，单线程可高效处理上万并发连接，不会因单个连接阻塞影响其他请求
4. 高效的数据结构：针对不同场景设计专属数据结构（如跳表、压缩列表、整数集合），既节省内存，又保证操作的高性能

# 四、Redis Zset 的实现原理是什么？

ZSet 的底层是跳表 + 哈希表双结构配合。跳表按 score 排序，支持 O(log N) 的插入、删除和范围查询；哈希表存 member 到 score 的映射，支持 O(1) 的单点查分

为什么要两个结构？各取所长：

1）通过 member 查 score，比如 ZSCORE key member，走哈希表，O(1) 搞定

2）按 score 范围查 member，比如 ZRANGEBYSCORE key 0 100，走跳表，O(log N + M)

3）插入和删除同时更新两个结构，跳表部分 O(log N)，哈希表部分 O(1)，整体 O(log N)

如果只用跳表，按 member 查 score 就得遍历，复杂度退化到 O(N)。如果只用哈希表，范围查询没法搞。两个结构各管各的，互补短板

当元素少的时候，ZSet 会用 listpack 来存，省内存。触发条件是元素个数不超过 128 且每个元素长度不超过 64 字节，任意一个条件破了就自动升级成跳表+哈希表。这俩阈值可以通过 zset-max-listpack-entries 和 zset-max-listpack-value 配置

# 五、为什么Redis设计为单线程?6.0版本为何引入多线程?

Redis 采用单线程设计的原因：

- 基于内存操作，多数操作性能瓶颈非 CPU 导致
- 单线程模型代码简便，可减少线程上下文切换的性能开销
- 单线程结合 I/O 多路复用模型能提高 I/O 利用率

Redis 6.0 版本引入多线程的原因：随着数据规模和请求量增加，执行瓶颈主要在网络 I/O，引入多线程可提高网络 I/O 处理速度

# 六、RDB（Redis DataBase）

RDB 是 Redis 的全量内存快照持久化。通过 fork 子进程，将瞬间内存数据写入 dump.rdb 二进制文件。优点是备份体积小、恢复速度快；缺点是两次快照之间可能存在数据丢失风险，且 fork 时可能引起瞬时内存消耗

两种 RDB 触发方式，一个阻塞一个不阻塞：

| 对比维度 | save 命令                          | bgsave 命令                        |
| ---------- | ------------------------------------ | ------------------------------------ |
| **执行方式**         | 由**Redis 主线程**亲自执行快照                     | Redis 主线程**fork 一个子进程**去执行                 |
| **是否阻塞**         | **阻塞**，快照完成前无法处理任何命令       | **不阻塞主线程**，客户端请求照常响应               |
| **适用场景**         | 停机维护、夜深人静的人工操作       | 所有在线生产环境                   |
| **比喻**         | 老板亲自去仓库盘货，整个店关门停业 | 老板派一个助手去盘货，店面照样营业 |

在生产环境中，优先使用`bgsave`以避免服务中断。定期执行（如每5分钟）可减少数据丢失风险，但需监控内存使用

# 七、AOF（Append Only File）

AOF 是 Redis 的写命令日志持久化。它的工作流程是追加命令到缓冲区 → 按 everysec/always/no 策略刷盘 → AOF 文件膨胀时触发 Rewrite 自动压缩 → 恢复时重放命令。优点是数据丢失极少，缺点是文件大、恢复比 RDB 慢

AOF 的三种同步策略：

| 对比维度 | appendfsync always     | appendfsync everysec   | appendfsync no         |
| ---------- | ------------------------ | ------------------------ | ------------------------ |
| **同步频率**         | 每一个写命令都同步刷盘 | **每秒**刷盘一次               | 完全交给操作系统决定   |
| **丢数据风险**         | **几乎不丢**                       | **最多丢 1 秒**数据                   | 系统宕机可能丢大量数据 |
| **对性能影响**         | 极大拉低 QPS           | 对性能影响极小，**最佳平衡点**       | 性能高，但不安全       |
| **比喻**         | 签完字立刻盖章入档     | 每整点所有签字统一盖章 | 随手扔桌，等保洁收走   |

AOF 工作流程四步走：

1. 命令追加：每条写命令追加到 AOF 缓冲区
2. 文件同步：根据appendfsync策略，将缓冲区write并 fsync 到磁盘的 AOF 文件
3. 文件重写：当 AOF 太大，fork 子进程，按内存当前数据生成最精简的写命令集，写入新 AOF 文件
4. 重启加载：创建一个伪客户端，把 AOF 所有命令重放一遍

# 八、两者的区别和选择方案

### RDB和AOF：快照 vs 日志

- **RDB**就是一个某个时间点的全量快照，二进制，恢复巨快，适合灾备。缺点就是两次快照之间的数据，没了。如果你每5分钟做一次bgsave，那崩溃时最多丢5分钟的数据
- **AOF**像写日记，每笔写操作都记下来。重启时按日记重放一遍就恢复了。但它文件会越来越大，所以需要`bgrewriteaof`，子进程根据当前内存数据写一份最小指令集，不影响主线程，做完替换旧文件

### RDB和AOF怎么选？

- 如果你说“我是缓存，数据数据库里都有，挂了重建就行”，那就只用RDB，或者干脆关掉持久化
- 如果你说“我存了用户签到状态、购物车，丢了用户会疯”，那就AOF everysec，并且也定期做RDB，双重保险
- 现在更推荐的是aof-use-rdb-preamble yes，混合持久化，既有RDB的快恢复，又有AOF的完整性

# 九、混合持久化

Redis 4.0 引入了混合持久化，通过aof-use-rdb-preamble yes开启。它在 AOF Rewrite 时，将当前内存数据以 RDB 二进制格式写入新 AOF 文件头部，后续命令仍以 AOF 格式追加。这样兼具 RDB 恢复快和 AOF 数据安全的优点，避免了纯 AOF 恢复慢的缺点。缺点是文件头人眼不可读、低版本不兼容

# 十、Reids的数据恢复

开启了混合持久化，仍然建议定期执行 RDB 全量备份，并将其与 AOF 文件一同传输到异地或对象存储（如 S3/OSS） 做离线容灾

在对数据丢失非常敏感的场景，应考虑使用云厂商提供的秒级数据闪回 (PITR) 功能，它提供了比原生恢复更精细、更方便的操作粒度

# 十一、缓存异常三大问题

缓存穿透查“不存在”，缓存击穿锁“一个点”，缓存雪崩崩“一整片”

| 对比维度 | 缓存穿透                 | 缓存击穿              | 缓存雪崩                   |
| ---------- | -------------------------- | ----------------------- | ---------------------------- |
| **问题本质**         | 查的数据根本不存在       | 一个热点key突然过期   | 大量key同时过期或Redis宕机 |
| **典型场景**         | 恶意攻击（用-1连续请求） | 秒杀商品到期那一瞬间  | 批量导入缓存设了相同TTL    |
| **核心解法**         | 布隆过滤器 + 空值缓存    | 热点永不过期 + 互斥锁 | TTL加随机值                |
| **难度**         | 低                       | 中                    | 高                         |

**布隆过滤器**：使用BitMap作为布隆过滤器，将目前所有可以访问到的资源通过简单的映射关系放入到布隆过滤器中（哈希计算），当一个请求来临的时候先进行布隆过滤器的判断，如果有那么才进行放行，否则就直接拦截

**空值缓存**：如果查询缓存和数据库的数据没有找到，则直接设置一个默认值（可以是空值）存到缓存中，这样第二次读取缓存时就会获取到默认值，而不会继续访问存数据库

**热点永不过期**：监控数据，实时调整:监控哪些数据是热门数据，实时的调整key的过期时长

**互斥锁**：热点key过期时，只让一个线程去查库重建缓存，其他线程等待结果，防止全部打垮数据库

**TTL加随机值**：将缓存失效时间分散开，比如可以在原有的失效时间基础上增加一个随机值，比如1-5分钟随机，这样每一个缓存的过期时间的重复率就会降低，就很难引发集体失效的事件

# 十二、双写一致性

#### 3种常用的缓存读写策略详解

1.**Cache Aside Pattern（旁路缓存模式）** 
Cache Aside Pattern 是我们平时使用比较多的一个缓存读写模式，比较适合读请求比较多的场景
Cache Aside Pattern 中服务端需要同时维系 db 和 cache，并且是以 db 的结果为准
写：
先更新 db
然后直接删除 cache 。
读 :
从 cache 中读取数据，读取到就直接返回
cache 中读取不到的话，就从 db 中读取数据返回
再把数据放到 cache 中
2.**Read/Write Through Pattern（读写穿透）** 
只更新缓存，由缓存自己同步更新数据库
写：
先查 cache，cache 中不存在，直接更新 db
cache 中存在，则先更新 cache，然后 cache 服务自己更新 db（同步更新 cache 和 db）
读：
从 cache 中读取数据，读取到就直接返回
读取不到的话，先从 db 加载，写入到 cache 后返回响应
3.**Write Behind Pattern（异步缓存写入）** 
只更新缓存，由缓存自己异步更新数据库

#### **怎么解决读写**

1.**若一致性要求高：强一致方案**
采用redisson实现的读写锁
在读的时候添加共享锁，可以保证读读不互斥，读写互斥(其他线程可以一起读，但是不能写)。当我们更新数据的时候，添加排他锁，它是读写，读读都互斥（其他线程不能读也不能写），这样就能保证在写数据的同时是不会让其他线程读数据的，避免了脏数据
2.**延时双删**
先删除缓存，再写数据库，然后线程休眠一段时间（比如500毫秒），最后再次删除缓存。休眠时间的确定需要评估项目读数据业务逻辑的耗时，并考虑Redis和数据库主从同步的耗时
优缺点：这种策略能在一定程度上解决数据不一致的问题，但增加了写请求的耗时，并且在最差的超时时间内，数据仍可能存在不一致性
3.**先写db再删除缓存策略**（推荐）
推荐理由：这是实时性最好的方案，适用于对并发和实时一致性要求较高的场景。如果删除Redis失败，则可以通过重试机制来解决
执行流程：先执行数据库的更新操作，成功后立即删除Redis中的对应缓存
优缺点：虽然在极少数情况下会出现数据不一致的情况，但其条件相对苛刻，是实时性要求下的最佳选择

# 十三、数据过期策略 vs 淘汰策略

过期策略管“该不该删”，淘汰策略管“满了删谁”

| 对比维度 | 惰性删除                    | 定期删除               | 数据淘汰策略（八种）     |
| ---------- | ----------------------------- | ------------------------ | -------------------------- |
| **触发时机**         | 访问key时检查               | 定时任务每秒轮询一部分 | 内存满了触发             |
| **删除对象**         | 已过期的key                 | 已过期的key            | 任意key（按策略挑）      |
| **优点**         | 对CPU友好                   | 对内存友好             | 保证Redis不会OOM         |
| **缺点**         | 过期key没被访问就永远占内存 | 轮询频率不好把握       | 可能删掉不该删的热点数据 |
| **比喻**         | 快递到了才拆，发现过期才扔  | 保洁每小时抽查一批     | 冰箱满了，按规则扔东西   |

**八种淘汰策略速记**：

| 类型    | 策略名          | 一句话                       |
| --------- | ----------------- | ------------------------------ |
| 不淘汰  | noeviction      | 满了直接报错                 |
| 全体key | allkeys-lru     | 淘汰最久没用的               |
| 全体key | allkeys-lfu     | 淘汰使用次数最少的           |
| 全体key | allkeys-random  | 随机淘汰                     |
| 带TTL的 | volatile-lru    | 有过期时间的，挑最久没用的删 |
| 带TTL的 | volatile-lfu    | 有过期时间的，挑用得最少的删 |
| 带TTL的 | volatile-random | 有过期时间的，随机删         |
| 带TTL的 | volatile-ttl    | 有过期时间的，挑快过期的删   |

LRU(least recently used)的意思就是最少最近使用，用当前时间减去最后一次访问时间，这个值越大则淘汰优先级越高
LFU(least frequently used)的意思是最少频率使用。会统计每个key的访问频率，值越小淘汰优先级越高
**选型建议**：

- 纯缓存，数据库都有备份 → allkeys-lru
- 有些缓存数据很重要不能丢 → volatile-lru
- 热点数据非常集中 → allkeys-lfu

# 十四、主从复制

三个作用：数据冗余备份、读写分离扛流量、故障恢复
主库负责写，从库负责读，流量大的时候把读请求全甩给从库，主库压力就下来了

# 十五、主从数据同步的流程

**第一阶段是：建立连接与全量同步**
当从节点第一次连上主节点时，会发送 PSYNC 命令。因为是第一次，主节点会执行一次全量复制
具体就是主节点会在后台生成一份 RDB 快照文件发给从节点，从节点拿到后先清空自己的旧数据，然后加载这份快照
在生成和发送快照的这段时间里，主节点是不会停止服务的，它会把这段时间新收到的写命令，先暂存在一个叫 Replication Buffer 的内存缓冲区里。等快照发完了，再把这个缓冲区里的命令发给从节点，这样就保证了数据不丢失
**第二阶段是：命令传播**
全量同步完成后，主从之间就会建立一个长连接。以后主节点每收到一个写命令，就会异步地发送给从节点，从节点跟着执行就好了。这期间他们还会互相发心跳包（Ping/Ack）来确认对方还活着
**第三阶段是：断线重连与增量同步**
网络总是不稳定的，如果从节点掉线了一小会儿又连上了，重新搞一次全量同步太浪费资源了
所以 Redis 2.8 以后引入了增量同步。主节点内部有一个环形的缓冲区叫 repl_backlog_buffer（积压缓冲区）
如果从节点连上来，告诉主节点：“我刚才读到偏移量 1000 了”，主节点一看积压缓冲区里 1000 之后的数据还在，就会只把断线期间这部分数据补发给从节点，这就叫增量复制
但如果断线太久，缓冲区的数据被覆盖了，那就只能无奈地重新发起全量同步了

# 十六、主从同步有几种方式？

三种
异步复制：主库提交完就走，不管从库，性能最好但可能丢数据
半同步：至少等一个从库确认收到binlog再返回，不丢数据但性能稍差
全同步：等所有从库执行完才返回，太慢了基本不用。生产环境一般用半同步

# 十七、哨兵

# **1.故障恢复过程是怎样的？**

哨兵就是Redis的高可用保镖，主库挂了它能自动选新主库恢复服务
流程四步：先监控主库心跳，发现主库失联就判主观下线，然后拉上其他哨兵投票确认客观下线，接着哨兵选出一个领导，最后由领导执行故障转移，把从库提成主库

# **2.哨兵的实现原理是什么？**

哨兵就是一台运行在特殊模式下的Redis实例，核心就干三件事：定时发PING监控所有节点，用发布订阅机制和其他哨兵交换信息，主库故障时用Raft算法选出一个领头哨兵去执行故障转移

## **（1）定时监控**

 Redis Sentinel 的定时监控由三个频率差异化的定时任务精密协同完成：
 **每秒 PING 一次** 所有节点做心跳检测，作为主观下线的直接依据；
 **每 2 秒 向 __sentinel__:hello 频道发布自身信息并订阅**，实现 Sentinel 节点的自动发现和主节点状态判断的共享；
 **每 10 秒 向主从节点发送 INFO 命令以更新拓扑结构**，感知从节点增删和主从关系变化。三者互不可替代，从存活检测、集群感知、拓扑维护三个维度，共同构建出对 Redis 集群的全方位、准实时的监控体系。

## **（2）主观下线和客观下线**

主观下线是一个哨兵自己判断主库挂了，可能误判
客观下线是多个哨兵投票，超过quorum个哨兵都说挂了才算真挂了。单独一人说了不算，大家一起举手才算数

## **（3）选举**

Sentinel 领导者选举是一个基于 纪元（epoch） 的分布式共识过程，它借鉴了 Raft 算法。
当某个 Sentinel 确认主节点客观下线后，将纪元号自增并请求其他 Sentinel 投票给自己，每个 Sentinel 在每个纪元内采用先到先得原则投票
获得超过半数票（多数派）的 Sentinel 成为本次故障转移的唯一领导者，负责执行主从切换。若一轮未选出，则纪元递增并引入随机休眠后重试，直至选出为止

## **（4）故障转移**

Redis Sentinel 的故障转移是一个由当选领导者 Sentinel 指挥的，包含**选主、升主、更新拓扑、通知客户端**四步的自动化流程
确认主库客观下线后，领导者根据从库优先级 → 复制偏移量 → Run ID 的三级排序选出最优从库，将其提升为主，并让其余从库跟随新主
同时，通过配置版本（纪元）强制将可能恢复的旧主降级为从，并利用发布/订阅机制通知客户端更新连接地址，完整实现秒级自动恢复

# **十八、Redis集群为什么要有？解决了什么问题？**

两个问题，单机存不下和单机扛不住。数据量太大一台机器内存装不下，海量数据得切片分到多台；并发量太高一台机器读写不过来，得分流。集群就是帮你把数据分片、负载分担

# **十九、数据怎么分片？什么是哈希槽？**

Redis集群用了16384个哈希槽，每个key用CRC16算一下，对16384取模，决定落到哪个槽。槽再分给不同节点，每个节点管一批槽。一句话：key算出一个数，按数值分到对应槽对应的机器上

# **二十、Redis集群怎么创建？**

先起节点，再用cluster meet让它们握手。核心动作就一个三节点握手：A用meet给B发请求，B收到后给A回PONG，A再给B发PING，两边互相认识了。所有节点两两连一遍，集群就建好了

# **二十一、分配槽怎么操作？**

答：用cluster addslots给节点指定槽范围。比如节点1管0到5000，节点2管5001到10000，节点3管10001到16383。槽分完集群才能正常工作，没分槽的节点啥数据都不存

# **二十二、Redis Cluster故障转移**

Redis Cluster 的故障转移是一个去中心化的自动恢复过程，分为三步：
首先，基于 Gossip 协议的 PING/PONG 心跳，节点超时未响应被标记为 PFAIL；当多数主节点确认后升级为 FAIL 并广播
其次，故障主节点的从节点以 Raft-like 算法竞选新主，数据越新发起越快、先到先得投票，只有获得超过半数主节点的赞同票才能胜出
最后，当选从节点升为新主并接管哈希槽，通过 Gossip 协议全网同步新配置

# **二十三、集群方案**

## **1.主从复制**

分全量和增量。全量同步就是主库生成RDB快照发给从库，从库先清空自己然后加载。增量同步是主库维护一个复制积压缓冲区，把写命令记下来，从库断线重连后从断开的位置接着追


## 2.哨兵模式(R**edis Sentinel）**

简单说：哨兵不处理数据，只管监控和故障恢复。盯着主节点心跳，主挂了就投票确认，然后选新主并通知其他节点更新路由。自动故障转移，人不用半夜爬起来切主库
复杂点：
哨兵模式模式是一套独立于 Redis 数据节点的、通过分布式共识实现自动故障转移的高可用方案
 它以奇数个哨兵（通常 ≥3）作为监控集群，通过定时心跳、发布/订阅信息和 INFO 查询多维度感知数据节点存活状态
当 Sentinel 集群对主节点宕机达成客观下线共识后，会在内部进行Raft-like 选举产生一个领导者 Sentinel，由该领导者从所有从节点中依据优先级、复制偏移量、Run ID 选出最优者提升为新主，并完成拓扑更新和客户端通知的全过程
相比于纯主从，Sentinel 模式升级为全自动秒级恢复；它架构简单，但受单机内存限制，适用于无需水平分片的高可用场景

### **脑裂是什么？怎么处理？**

集群分裂成多个小团伙，都以为自己是对的，可能两个节点同时写数据导致数据不一致。处理方案是设置参数，当从库数量不够的时候主库拒绝写入，自己主动停写先保证数据不脏

## **3.分片集群（Redis cluster）**

哨兵模式解决了主从复制不能自动故障转移、达不到高可用的问题，但还是存在主节点的写能力、容量受限于单机配置的问题。而cluster模式实现了Redis的分布式存储，每个节点存储不同的内容，解决主节点的写能力、容量受限于单机配置的问题

它通过数据分片将海量数据打散到多个主节点，实现了水平扩展；
通过无中心的 Gossip 协议，各个节点对等通信、共享元数据，实现了去中心化的高可用；
通过内置的故障转移机制，在主节点宕机时由其他主节点投票完成自动切换，无需外部哨兵

### **数据的存储和读取**

Redis 集群引入了哈希槽的概念，有 16384 个哈希槽，集群中每个主节点绑定了一定范围的哈希槽范围， key通对 16384 取模来决定放置哪个槽，通过槽找到对应的节点进行存储

# **二十四、分布式锁用Redis怎么实现？**

就用`SET key value NX EX 30`，NX保证互斥，EX设过期防止死锁。一定要SET和EX原子操作，别分两步，不然刚SET完就挂了，锁永远不释放

# **二十五、为什么要用Lua脚本**

它是用来解决Redis单命令原子性不能满足的组合操作竞态问题的

# **二十六、锁的有效时长怎么控制？**

根据业务执行时间预估，一般设个30秒左右。但有个坑，业务没跑完锁过期了怎么办？搞一个看门狗线程，定期检查业务没完就延长锁时间，Redisson就是这么干的，锁续期自动续

# **二十七、redission实现的分布式锁**

Redisson基于Redis，通过 “Hash数据结构 + Lua原子脚本 + 看门狗(Watchdog)自动续期” 三大机制，提供了一个安全、可重入且语义清晰的企业级分布式锁。它根除了手写SETNX实现中的锁过期、不可重入和误删三大痛点，通过 lock,tryLock 等语义化API，平衡了可靠性与高性能

# **二十八、可重入锁什么意思？怎么实现？**

同一个线程可以多次拿同一把锁，不会自己卡死自己。Redis实现就是在value里存个线程标识和计数器，加锁的时候判断是不是自己，是自己就计数加1，解锁计数减1，减到0才真释放

# **二十九、主从一致性在分布式锁里有什么问题？**

主库加锁，还没同步到从库，主库挂了，从库升主，但是锁丢了，其他线程又能加了
解决方案是
RedLock通过向多个独立Redis实例加锁，超过半数成功才算拿到，显著提高了数据安全性。但需要提醒的是，它在极端网络场景下并非绝对一致。对于普通业务，Redisson的单实例加主从哨兵模式基本够用；对于金融级场景，建议直接用ZooKeeper或etcd这类基于Raft算法的强一致性锁

# **三十、Redis为什么单线程还那么快？**

四大原因。纯内存操作纳秒级，单线程无锁竞争无上下文切换，IO多路复用一个线程管上万连接，数据结构专门优化过。总结就是：内存快、无切换、复用IO、结构精简

# **三十一、大key有什么问题？怎么找到？怎么处理？**

大key就是单个key的value太大，删了会导致Redis阻塞，读写也慢，内存分布不均。怎么找？用`redis-cli --bigkeys`扫一遍，或者用`memory usage key`看大小。怎么处理？优雅的删法是用`UNLINK key(异步删除)`，但大key删还是会卡，更好的办法是分批渐进式删。设计阶段就拆分大key，把一个大哈希表拆成多个小哈希表

# **三十二、热key怎么判定？怎么处理？**

热key就是某一个key被大量请求打爆了。怎么发现？用`redis-cli --hotkeys`，或者提前用`redis-cli`的`monitor`观察热点，或者客户端侧做统计。怎么处理？热点key重建用互斥锁，只让一个线程查库，其他等着；缓存预热就是提前把热点数据加载好，别等用户来了再查。还有一个办法是二级缓存，本地缓存扛一层，Redis扛下一层

# **三十三、Redis有事务吗？原理是什么？**

有，但它的事务很简单，核心是MULTI、EXEC、DISCARD。MULTI开启事务，把命令排队，EXEC一起执行，DISCARD取消。注意两点：它不支持回滚，中间某条命令语法错了全不执行，但运行时出错别的照样执行；如果是Watch+事务的方式可以实现乐观锁的效果

# **三十四、缓存预热**

本质上，它是‘空间换时间’的典型应用，用启动时的额外开销和内存，去交换服务稳态下的低延迟，核心解决缓存冷启动时的性能坍塌。
在落地策略上，我把它分为两类：
第一，全量预热，适用于数据量小、命中率要求极高的场景，比如基础配置、黑名单库。代价是启动慢、内存占用大
第二，热点预热，适用于海量数据的缓存，比如内容平台的热门推荐。依赖对热点数据的精准预测，成本低但预测不准时效果会打折扣
预热必须配套过期策略与更新机制，否则会引入脏数据风险
